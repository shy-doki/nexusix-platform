## 1. 测试环境说明

### 1.1 环境配置

| 配置项 | 值 |
|--------|-----|
| 基础URL | `http://localhost:8081/NexusIxService` |
| 认证方式 | Header `NexusIX: {token}` |
| 登录接口 | `POST /auth/login` |
| 测试工具 | Apifox |
| 主租户 | TENANT_A（id=7001，is_primary=true） |
| 数据库 | PostgreSQL |
| 缓存 | Redis |
| 操作系统 | Windows |

### 1.2 技术栈

- Spring Boot 3.3.4
- MyBatis-Plus 3.5.12
- Sa-Token（认证框架）
- PostgreSQL（主数据库，JSONB 存储扩展属性）
- Redis（Session缓存）

### 1.3 统一响应格式

#### 1.3.1 成功响应

```json
{
  "code": 200,
  "msg": "success",
  "data": {
    // 业务数据
  }
}
```

#### 1.3.2 错误响应

```json
{
  "code": 500,
  "msg": "错误描述信息",
  "data": null
}
```

### 1.4 认证说明

所有需认证的接口必须在请求头携带 `NexusIX` 字段，值为登录后获取的 Token。

| Header 参数 | 是否必填 | 说明 | 示例值 |
|-------------|---------|------|--------|
| NexusIX | 是 | 认证Token | abc123def456ghi789 |
| Content-Type | 是（POST/PUT/DELETE Body接口） | 内容类型 | application/json |

## 3. 通用说明

### 3.1 4级权限禁用体系

NexusIX-Platform 采用 **SYSTEM > TENANT > DEPT > ROLE > USER** 的4级权限继承体系：

| 级别 | target_type | 说明 | 影响范围 |
|------|-------------|------|----------|
| 系统级 | SYSTEM（预留） | 全局禁用，影响所有租户 | 当前未实现 |
| 租户级 | TENANT | 针对某个租户禁用权限 | 影响该租户下所有用户 |
| 部门级 | DEPT | 针对某个租户下的部门禁用权限 | 影响该部门下所有用户 |
| 角色级 | ROLE | 针对某个租户下的角色禁用权限 | 影响该角色下所有用户 |
| 用户级 | USER | 针对某个用户在某租户下的禁用权限 | 仅影响该用户 |

### 3.2 物化路径树形结构说明

租户表采用物化路径（Materialized Path）模型存储层级关系：

| 字段 | 说明 | 示例 |
|------|------|------|
| parent_id | 父租户ID | 111 |
| path | 祖级路径，根节点为 /{id} | /101/111/121 |
| level | 层级深度，根节点为1 | 3 |
| has_children | 是否存在子租户 | true/false |

**树形结构示例**：
```
万象集团(101) path=/101 level=1
├── 万象-华东分公司(111) path=/101/111 level=2
│   ├── 万象-华东-上海办事处(121) path=/101/111/121 level=3
│   └── 万象-华东-南京办事处(122) path=/101/111/122 level=3
├── 万象-华南分公司(112) path=/101/112 level=2
└── 万象-华北分公司(113) path=/101/113 level=2 [DISABLED]
```

### 3.3 测试用例编号规则

- `TC-X.Y.Z`：业务场景测试用例，X=章节号，Y=接口号，Z=用例序号
- `PT-X.Y.Z`：压测场景用例

### 3.4 Apifox 通用配置

#### 3.4.1 环境变量配置

在 Apifox 中配置环境变量：

| 变量名 | 类型 | 初始值 | 说明 |
|--------|------|--------|------|
| baseUrl | string | http://localhost:8081/NexusIxService | 基础URL |
| token | string | （登录后自动写入） | 认证Token |
| testTenantId | string | 7001 | 测试租户A的ID |
| testTenantCode | string | TENANT_A | 测试租户A的编码 |
| testPolicyCode | string | TP_DEPT_001 | 测试策略编码 |

#### 3.4.2 全局请求头配置

```
NexusIX: {{token}}
Content-Type: application/json
```

#### 3.4.3 后置脚本（自动提取Token）

在登录接口的后置脚本中添加：

```javascript
// 提取Token并写入环境变量
var jsonData = pm.response.json();
if (jsonData.code === 200 && jsonData.data && jsonData.data.token) {
    pm.environment.set("token", jsonData.data.token);
}
```

## 6. 压测总体说明

### 6.1 压测目标

本章对租户管理模块（SysTenantController 与 SysTenantPolicyController）的 36 个接口进行压测总体说明，旨在：

1. **验证系统容量**：评估各接口在不同并发负载下的吞吐量（TPS）与响应时间（RT）
2. **识别性能瓶颈**：定位数据库慢查询、连接池耗尽、锁竞争等潜在问题
3. **保障稳定性**：确保高并发场景下错误率可控，无内存泄漏与连接泄漏
4. **指导容量规划**：为生产环境资源规划（数据库连接池、线程池、Redis 连接数）提供数据依据

### 6.2 压测环境配置

| 配置项 | 值 |
|--------|-----|
| 基础URL | `http://localhost:8081/NexusIxService` |
| 认证方式 | Header `NexusIX: {token}` |
| 压测工具 | Apifox |
| 数据库 | PostgreSQL |
| 缓存 | Redis |
| 测试数据量 | 租户表 14 条，租户策略表 30+ 条 |
| 并发模型 | 阶梯加压（每30秒增加并发用户） |

### 6.3 压测指标说明

| 指标 | 缩写 | 说明 | 期望值 |
|------|------|------|--------|
| 每秒事务数 | TPS | 每秒成功处理的请求数 | 查询类≥100，写入类≥20 |
| 响应时间 | RT | 请求从发出到接收完整响应的时间 | P95≤500ms（查询），P95≤1000ms（写入） |
| 错误率 | Error Rate | 失败请求占总请求的百分比 | ≤1%（正常负载），≤5%（峰值负载） |
| 并发用户数 | VU | 同时发起请求的虚拟用户数 | 20/50/100/200 |
| 思考时间 | Think Time | 用户操作之间的间隔时间 | 100ms-1000ms 随机 |

| 持续时间 | 实际运行时长 |

### 6.7 Apifox 压测通用配置步骤

1. **环境配置**：在 Apifox 中配置环境变量 `baseUrl=http://localhost:8081/NexusIxService`，`token={{token}}`
2. **接口导入**：将本文档中的 curl 示例导入 Apifox 接口定义
3. **测试场景创建**：按 6.4.2 优先级创建测试场景，组合相关接口
4. **参数化**：使用 CSV 文件参数化 tenantId、policyCode、tenantCode 等变量，避免数据冲突
5. **断言配置**：为每个接口配置响应断言（code=200、data 非空等）
6. **并发设置**：按各接口压测方案配置并发用户数、持续时间、加压策略
7. **执行与监控**：启动压测，实时监控 TPS、RT、错误率
8. **结果分析**：压测结束后导出报告，按 6.6 模板记录结果，分析瓶颈并优化

### 6.8 压测注意事项

1. **数据隔离**：压测产生的数据应使用独立策略编码（如 `TP_PT_` 前缀），便于压测后清理
2. **状态恢复**：涉及状态变更的压测（如禁用策略）结束后需恢复数据至 ACTIVE 状态
3. **登录态有效期**：Sa-Token 存在有效期，长时间压测需配置 Token 自动续期或定时刷新
4. **数据库连接池**：压测前确认 HikariCP maximum-pool-size 配置（建议≥20），避免连接等待
5. **缓存预热**：查询类压测前先执行若干次请求，避免冷启动影响首次测量结果
6. **事务回滚**：批量操作压测中若出现部分失败，需确认事务是否回滚，避免脏数据
