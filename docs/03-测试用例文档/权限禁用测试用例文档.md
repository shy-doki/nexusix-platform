## 1. 文档概述

### 1.1 文档目的

本文档用于验证 NexusIX-Platform 多租户 SaaS 平台的 **4级权限禁用体系** 是否在各种场景下都能正确工作。测试覆盖：

- 单级别禁用（TENANT / DEPT / ROLE / USER）
- 多级别组合禁用
- 跨租户隔离性
- 字段级权限禁用
- 禁用状态恢复
- 权限主表（sys_perm）禁用与策略表（sys_perm_policy）禁用的区别

### 1.2 4级权限禁用体系说明

NexusIX-Platform 采用 **SYSTEM > TENANT > DEPT > ROLE > USER** 的4级权限继承体系（SYSTEM级为系统预留，当前实现中尚未产生SYSTEM级禁用记录）：

| 级别 | target_type | 说明 | SQL查询路径 |
|------|-------------|------|-------------|
| 系统级 | SYSTEM（预留） | 全局禁用，影响所有租户 | 当前未实现 |
| 租户级 | TENANT | 针对某个租户禁用权限 | sys_user_policy(TENANT) → sys_tenant → sys_perm_policy(TENANT) |
| 部门级 | DEPT | 针对某个租户下的部门禁用权限 | sys_user_policy(TENANT) → sys_user_policy(DEPT) → sys_tenant_policy(DEPT) → sys_perm_policy(DEPT) |
| 角色级 | ROLE | 针对某个租户下的角色禁用权限 | sys_user_policy(TENANT) → sys_user_policy(ROLE) → sys_tenant_policy(ROLE) → sys_perm_policy(ROLE) |
| 用户级 | USER | 针对某个用户在某租户下的禁用权限 | sys_user_policy(TENANT) → sys_perm_policy(USER) |

**禁用机制**：通过将 `sys_perm_policy.status` 设置为 `DISABLED`，权限不会从用户的启用列表中消失，而是出现在禁用列表中，前端可根据禁用级别决定是否显示灰色按钮或隐藏菜单。

### 2.3 数据库验证SQL（查询用户当前权限状态）

执行以下SQL可查看 test_all 用户在所有租户下的完整权限视图（与 `queryUserAllPermInfo` 等价的手工查询）：

```sql
-- 查询 test_all 用户所有权限策略的当前状态
-- 按租户、权限编码、目标类型排序，便于核对
SELECT
    t.tenant_code AS tenant_code,
    p.perm_code AS perm_code,
    p.perm_name AS perm_name,
    pp.target_type AS target_type,
    pp.policy_code AS policy_code,
    pp.status AS policy_status,
    pp.table_name AS table_name,
    pp.field_operation AS field_operation
FROM sys_user_policy up_tenant
INNER JOIN sys_tenant t ON t.id = up_tenant.target_id
    AND up_tenant.target_type = 'TENANT'
    AND t.status = 'ENABLED'
    AND t.is_deleted = 'NOT_DELETED'
INNER JOIN sys_perm_policy pp ON pp.is_deleted = 'NOT_DELETED'
    AND (
        -- TENANT级
        (pp.target_type = 'TENANT' AND pp.target_id = t.id)
        -- USER级
        OR (pp.target_type = 'USER' AND pp.target_id = up_tenant.id)
    )
LEFT JOIN sys_perm_policy pp_parent ON pp_parent.id = pp.perm_id
INNER JOIN sys_perm p ON p.id = COALESCE(pp_parent.perm_id, pp.perm_id)
    AND p.status = 'ENABLED'
    AND p.is_deleted = 'NOT_DELETED'
WHERE up_tenant.user_id = 7301
  AND up_tenant.status = 'ACTIVE'
  AND up_tenant.is_deleted = 'NOT_DELETED'

UNION ALL

-- ROLE级 + DEPT级（通过sys_user_policy和sys_tenant_policy关联）
SELECT
    t.tenant_code AS tenant_code,
    p.perm_code AS perm_code,
    p.perm_name AS perm_name,
    pp.target_type AS target_type,
    pp.policy_code AS policy_code,
    pp.status AS policy_status,
    pp.table_name AS table_name,
    pp.field_operation AS field_operation
FROM sys_user_policy up_tenant
INNER JOIN sys_tenant t ON t.id = up_tenant.target_id
    AND up_tenant.target_type = 'TENANT'
    AND t.status = 'ENABLED'
    AND t.is_deleted = 'NOT_DELETED'
INNER JOIN sys_user_policy up_sub ON up_sub.user_id = up_tenant.id
    AND up_sub.target_type IN ('ROLE', 'DEPT')
    AND up_sub.status = 'ACTIVE'
    AND up_sub.is_deleted = 'NOT_DELETED'
INNER JOIN sys_tenant_policy tp ON tp.id = up_sub.target_id
    AND tp.source_type = up_sub.target_type
    AND tp.tenant_id = t.id
    AND tp.status = 'ACTIVE'
    AND tp.is_deleted = 'NOT_DELETED'
INNER JOIN sys_perm_policy pp ON pp.is_deleted = 'NOT_DELETED'
    AND pp.target_type = up_sub.target_type
    AND pp.target_id = tp.id
LEFT JOIN sys_perm_policy pp_parent ON pp_parent.id = pp.perm_id
INNER JOIN sys_perm p ON p.id = COALESCE(pp_parent.perm_id, pp.perm_id)
    AND p.status = 'ENABLED'
    AND p.is_deleted = 'NOT_DELETED'
WHERE up_tenant.user_id = 7301
  AND up_tenant.status = 'ACTIVE'
  AND up_tenant.is_deleted = 'NOT_DELETED'
ORDER BY tenant_code, perm_code, target_type;
```

### 3.3 与4级权限体系的对应关系

```
┌─────────────────────────────────────────────────────────────┐
│                    用户登录响应 permInfo                      │
├─────────────────────────────────────────────────────────────┤
│  current.enabled   ← 当前主租户(TENANT_A)中 status=ACTIVE   │
│  current.disabled  ← 当前主租户(TENANT_A)中 status=DISABLED │
├─────────────────────────────────────────────────────────────┤
│  disabledDetailByTenant (按租户分组)                         │
│  ├── TENANT_A                                               │
│  │   ├── system: []  (SYSTEM级，预留)                        │
│  │   ├── tenant: []  (target_type=TENANT 的禁用权限)         │
│  │   ├── dept:   []  (target_type=DEPT 的禁用权限)           │
│  │   ├── role:   []  (target_type=ROLE 的禁用权限)           │
│  │   └── user:   []  (target_type=USER 的禁用权限)           │
│  ├── TENANT_B: { system, tenant, dept, role, user }         │
│  └── TENANT_C: { system, tenant, dept, role, user }         │
└─────────────────────────────────────────────────────────────┘
```

**关键规则**：
1. `disabledDetailByTenant` 中的权限code **不去重跨级别**——同一个权限code可以同时出现在 `tenant` 和 `dept` 列表中（表示多级别同时禁用）。
2. 每个列表内部 **去重**——同一个权限code在同一级别列表中只出现一次。
3. **所有租户都有完整的5个列表结构**——即使没有禁用权限的租户也会有空列表（这是修复2的成果，见第6章）。

## 4. 权限查询SQL分析

### 4.1 queryUserAllPermInfo 概述

核心SQL位于 `nexusix-iam/src/main/resources/mapper/SysPermPolicyMapper.xml`，通过 **UNION ALL** 合并4个查询，分别对应 TENANT / USER / ROLE / DEPT 四个级别。

> **关键修复**：4个查询中 **不再包含** `pp.status = 'ACTIVE'` 过滤条件。这意味着 DISABLED 状态的策略也会被查询出来，从而能够出现在 `current.disabled` 和 `disabledDetailByTenant` 中。详见第6章问题1。

### 4.2 TENANT级查询（Query 0）

```sql
SELECT ...
FROM sys_user_policy up_tenant                              -- ① 用户的租户绑定
INNER JOIN sys_tenant t ON t.id = up_tenant.target_id       -- ② 关联租户表
    AND up_tenant.target_type = 'TENANT'
    AND t.status = 'ENABLED'                                --    租户必须启用
    AND t.is_deleted = 'NOT_DELETED'
INNER JOIN sys_perm_policy pp ON pp.target_type = 'TENANT'  -- ③ 关联权限策略
    AND pp.target_id = t.id                                 --    target_id = 租户ID
    AND pp.is_deleted = 'NOT_DELETED'                       --    注意：无 pp.status 过滤
LEFT JOIN sys_perm_policy pp_parent ON pp_parent.id = pp.perm_id  -- ④ 父策略继承
INNER JOIN sys_perm p ON p.id = COALESCE(pp_parent.perm_id, pp.perm_id)  -- ⑤ 解析最终权限
    AND p.status = 'ENABLED'                                --    权限主表必须启用
    AND p.is_deleted = 'NOT_DELETED'
WHERE up_tenant.user_id = #{userId}
  AND up_tenant.status = 'ACTIVE'                           --    用户租户绑定必须ACTIVE
  AND up_tenant.is_deleted = 'NOT_DELETED'
```

**JOIN逻辑说明**：
- `up_tenant`：从 `sys_user_policy` 查出用户的所有租户绑定（id=77001/77002/77003）
- `pp.target_id = t.id`：权限策略的 target_id 直接等于租户ID（如7001）
- `COALESCE(pp_parent.perm_id, pp.perm_id)`：如果 `pp.perm_id` 指向另一个策略（如80002），则取父策略的 perm_id；否则直接用 `pp.perm_id`

### 4.3 USER级查询（Query 1）

```sql
SELECT ...
FROM sys_user_policy up_tenant
INNER JOIN sys_tenant t ON ...
INNER JOIN sys_perm_policy pp ON pp.target_type = 'USER'
    AND pp.target_id = up_tenant.id                         -- ★ target_id = 用户租户绑定ID（77001等）
    AND pp.is_deleted = 'NOT_DELETED'
LEFT JOIN sys_perm_policy pp_parent ON ...
INNER JOIN sys_perm p ON ...
WHERE up_tenant.user_id = #{userId}
  AND up_tenant.status = 'ACTIVE'
  AND up_tenant.is_deleted = 'NOT_DELETED'
```

**关键点**：USER级策略的 `target_id` 不是用户ID（7301），而是 **用户租户绑定记录的ID**（77001/77002/77003）。这表示"用户在某个租户下"的特殊授权。

### 4.4 ROLE级查询（Query 2）

```sql
SELECT ...
FROM sys_user_policy up_tenant                              -- ① 用户租户绑定
INNER JOIN sys_tenant t ON ...
INNER JOIN sys_user_policy up_role ON up_role.user_id = up_tenant.id  -- ② 用户角色绑定
    AND up_role.target_type = 'ROLE'
    AND up_role.status = 'ACTIVE'
    AND up_role.is_deleted = 'NOT_DELETED'
INNER JOIN sys_tenant_policy tp_role ON tp_role.id = up_role.target_id  -- ③ 角色租户策略
    AND tp_role.source_type = 'ROLE'
    AND tp_role.tenant_id = t.id                            -- ★ 角色必须属于当前租户
    AND tp_role.status = 'ACTIVE'
    AND tp_role.is_deleted = 'NOT_DELETED'
INNER JOIN sys_role r ON r.id = tp_role.source_id           -- ④ 角色主表
    AND r.status = 'ENABLED'
    AND r.is_deleted = 'NOT_DELETED'
INNER JOIN sys_perm_policy pp ON pp.target_type = 'ROLE'
    AND pp.target_id = tp_role.id                           -- ★ target_id = 角色租户策略ID（76001等）
    AND pp.is_deleted = 'NOT_DELETED'
LEFT JOIN sys_perm_policy pp_parent ON ...
INNER JOIN sys_perm p ON ...
WHERE up_tenant.user_id = #{userId}
  AND up_tenant.status = 'ACTIVE'
  AND up_tenant.is_deleted = 'NOT_DELETED'
```

**JOIN链**：`用户 → 用户租户绑定(up_tenant) → 用户角色绑定(up_role) → 角色租户策略(tp_role) → 权限策略(pp) → 权限(p)`

**关键过滤**：`tp_role.tenant_id = t.id` 确保角色属于当前租户（跨租户隔离）。

### 4.5 DEPT级查询（Query 3）

```sql
SELECT ...
FROM sys_user_policy up_tenant
INNER JOIN sys_tenant t ON ...
INNER JOIN sys_user_policy up_dept ON up_dept.user_id = up_tenant.id  -- ② 用户部门绑定
    AND up_dept.target_type = 'DEPT'
    AND up_dept.status = 'ACTIVE'
    AND up_dept.is_deleted = 'NOT_DELETED'
INNER JOIN sys_tenant_policy tp_dept ON tp_dept.id = up_dept.target_id  -- ③ 部门租户策略
    AND tp_dept.source_type = 'DEPT'
    AND tp_dept.tenant_id = t.id                            -- ★ 部门必须属于当前租户
    AND tp_dept.status = 'ACTIVE'
    AND tp_dept.is_deleted = 'NOT_DELETED'
INNER JOIN sys_dept d ON d.id = tp_dept.source_id           -- ④ 部门主表
    AND d.status = 'ENABLED'
    AND d.is_deleted = 'NOT_DELETED'
INNER JOIN sys_perm_policy pp ON pp.target_type = 'DEPT'
    AND pp.target_id = tp_dept.id                           -- ★ target_id = 部门租户策略ID（75001等）
    AND pp.is_deleted = 'NOT_DELETED'
LEFT JOIN sys_perm_policy pp_parent ON ...
INNER JOIN sys_perm p ON ...
WHERE up_tenant.user_id = #{userId}
  AND up_tenant.status = 'ACTIVE'
  AND up_tenant.is_deleted = 'NOT_DELETED'
ORDER BY tenantCode, permCode
```

**JOIN链**：`用户 → 用户租户绑定(up_tenant) → 用户部门绑定(up_dept) → 部门租户策略(tp_dept) → 权限策略(pp) → 权限(p)`

### 4.6 权限策略继承机制（COALESCE处理）

```sql
LEFT JOIN sys_perm_policy pp_parent ON pp_parent.id = pp.perm_id
INNER JOIN sys_perm p ON p.id = COALESCE(pp_parent.perm_id, pp.perm_id)
```

**两种情况**：

| 情况 | pp.perm_id 指向 | COALESCE 结果 | 示例 |
|------|-----------------|---------------|------|
| 直接权限 | sys_perm.id | pp.perm_id | 80001: perm_id=7401 → p.id=7401 (MENU_DASHBOARD) |
| 继承权限 | sys_perm_policy.id（父策略） | pp_parent.perm_id | 81001: perm_id=80002 → pp_parent=80002(perm_id=7431) → p.id=7431 (DATA_USER) |

**继承场景示例**：
- 策略 81001（PP_DEPT_RD_A_BTN）的 `perm_id=80002`
- 80002 是另一个策略（PP_TENANT_A_DATA），其 `perm_id=7431`
- COALESCE 解析：`pp_parent.perm_id=7431` → 最终权限为 DATA_USER
- 这样部门级策略可以"继承"租户级策略的权限定义，只需覆盖 `table_name`/`field_operation`/`data_scope`

## 6. 已知问题与修复记录

### 6.1 问题1：TC-03部门级禁用不显示在disabled列表

**问题描述**：
执行 TC-03（部门级禁用，将 `sys_perm_policy` id=81001 的 status 设为 DISABLED）后，登录响应中 `disabledDetailByTenant.TENANT_A.dept` 为空数组 `[]`，预期的 `["DATA_USER"]` 未出现。

**根本原因**：
`SysPermPolicyMapper.xml` 的 `queryUserAllPermInfo` 方法中，4个UNION ALL查询都包含了 `pp.status = 'ACTIVE'` 过滤条件。该条件会过滤掉所有 status=DISABLED 的策略记录，导致禁用状态的策略无法被查询出来，AuthServiceImpl 也就无法收集到禁用权限信息。

**修复方案**：
移除4个UNION ALL查询中的 `AND pp.status = 'ACTIVE'` 条件，保留 `pp.is_deleted = 'NOT_DELETED'` 条件。这样 DISABLED 状态的策略也会被查询出来，AuthServiceImpl 中的禁用收集逻辑（190-224行）才能正确工作。

**修复前SQL（部分示例）**：
```sql
-- 修复前（有问题）
INNER JOIN sys_perm_policy pp ON pp.target_type = 'DEPT'
    AND pp.target_id = tp_dept.id
    AND pp.is_deleted = 'NOT_DELETED'
    AND pp.status = 'ACTIVE'        -- ← 问题所在：过滤了DISABLED策略
```

**修复后SQL**：
```sql
-- 修复后（正确）
INNER JOIN sys_perm_policy pp ON pp.target_type = 'DEPT'
    AND pp.target_id = tp_dept.id
    AND pp.is_deleted = 'NOT_DELETED'
    -- 移除了 pp.status = 'ACTIVE'，允许DISABLED策略被查询
```

**影响范围**：
- 文件：`nexusix-iam/src/main/resources/mapper/SysPermPolicyMapper.xml`
- 方法：`queryUserAllPermInfo`
- 影响的4个UNION ALL查询：TENANT级（Query 0）、USER级（Query 1）、ROLE级（Query 2）、DEPT级（Query 3）

**验证方式**：
执行 TC-03，确认 `disabledDetailByTenant.TENANT_A.dept` = ["DATA_USER"]。

### 6.2 问题2：部分租户的DisabledDetail结构不完整

**问题描述**：
当只有部分租户有禁用权限时，`disabledDetailByTenant` 中只为有禁用权限的租户创建了 DisabledDetail 对象，没有禁用权限的租户缺失该字段。前端遍历 `disabledDetailByTenant` 时会因字段缺失而报错。

**示例**：
```json
// 修复前（有问题）
{
  "disabledDetailByTenant": {
    "TENANT_A": { "system": [], "tenant": ["MENU_DASHBOARD"], "dept": [], "role": [], "user": [] }
    // TENANT_B 和 TENANT_C 缺失！
  }
}
```

**根本原因**：
AuthServiceImpl 的禁用详情收集逻辑（190-224行）只在遇到 `permPolicyStatus != 'ACTIVE'` 的权限时才创建 DisabledDetail 对象。如果某个租户的所有权限都是ACTIVE，该租户不会出现在 `disabledDetailByTenant` Map 中。

**修复方案**：
在 AuthServiceImpl.java 的389-399行添加补全循环，遍历 `permsByTenant` 的所有租户，为没有 DisabledDetail 的租户创建完整的5个空列表结构：

```java
// 补全：确保所有租户都有完整结构
for (String tenantCode : permsByTenant.keySet()) {
    if (!disabledDetailByTenant.containsKey(tenantCode)) {
        UserContextDTO.DisabledDetail detail = new UserContextDTO.DisabledDetail();
        detail.setSystem(new ArrayList<>());
        detail.setTenant(new ArrayList<>());
        detail.setDept(new ArrayList<>());
        detail.setRole(new ArrayList<>());
        detail.setUser(new ArrayList<>());
        disabledDetailByTenant.put(tenantCode, detail);
    }
}
permissionInfo.setDisabledDetailByTenant(disabledDetailByTenant);
```

**修复后**：
```json

{
  "disabledDetailByTenant": {
    "TENANT_A": { "system": [], "tenant": ["MENU_DASHBOARD"], "dept": [], "role": [], "user": [] },
    "TENANT_B": { "system": [], "tenant": [], "dept": [], "role": [], "user": [] },
    "TENANT_C": { "system": [], "tenant": [], "dept": [], "role": [], "user": [] }
  }
}
```

**影响范围**：
- 文件：`nexusix-iam/src/main/java/com/shy/nexusix/iam/service/impl/AuthServiceImpl.java`
- 代码行：389-399行
- 方法：`login`

## 7. 测试结论

### 7.1 功能验证总结

| 验证项 | 状态 | 对应用例 | 说明 |
|--------|------|----------|------|
| 4级权限禁用体系 | ✅ 通过 | TC-01 ~ TC-04 | TENANT/DEPT/ROLE/USER 级别禁用均能正确出现在对应列表 |
| 多级别组合禁用 | ✅ 通过 | TC-05, TC-12 ~ TC-15 | 同权限多级别禁用独立记录，不互相覆盖 |
| 跨租户隔离性 | ✅ 通过 | TC-06, TC-17 | 一个租户的禁用不影响其他租户 |
| 字段级权限禁用 | ✅ 通过 | TC-07 | field_operation 中的字段正确移入 inoperable |
| 状态恢复 | ✅ 通过 | TC-08 | DISABLED → ACTIVE 后权限恢复正常 |
| 主表禁用 vs 策略禁用 | ✅ 通过 | TC-09 ~ TC-11, TC-16 | 主表禁用使权限完全消失，策略禁用保留在disabled列表 |
| DisabledDetail结构完整性 | ✅ 通过 | 所有用例 | 所有租户都有完整的5个列表结构（修复2验证） |

### 7.2 关键行为总结

1. **策略禁用（pp.status=DISABLED）**：权限出现在 `current.disabled` 和 `disabledDetailByTenant` 对应级别列表中，前端可据此显示灰色按钮或隐藏菜单。
2. **主表禁用（p.status=DISABLED）**：权限完全从响应中消失，既不在enabled也不在disabled中。这是"硬禁用"，适用于权限下线场景。
3. **权限去重**：基于 `permCode + tenantCode` 去重，取UNION ALL的第一条记录（TENANT > USER > ROLE > DEPT 顺序）。如果TENANT级策略DISABLED，即使DEPT级策略ACTIVE，权限仍归入disabled。
4. **disabledDetailByTenant跨级别独立**：同一权限可同时出现在多个级别列表中（如tenant+dept+role+user），各列表独立去重。
5. **所有租户结构完整**：即使没有禁用权限的租户也有完整的5个空列表，避免前端字段缺失错误。
